# BIZ01 · 오픈 코어·소스·산출물 권리

상태: 승인된 Foundation 1.0.0 설계 기준선 · 검토 2026-09-13

책임 역할: 사업/마케팅 담당. 이 문서의 설계는 아직 제품 구현·실행 검증 완료를 뜻하지 않는다.

## 사용자가 소유하는 것과 Axiom이 제공하는 서비스

사용자가 만든 디자인 시스템 문서와 출력 코드가 구독 종료와 함께 쓸 수 없게 되면 “사용자 소유 UI 라이브러리”라는 가치가 사라진다. 문서·자산·생성 코드의 지속 사용과 이식은 기본 제품 원칙이다. 다만 포함된 폰트·이미지·라이브러리의 제3자 조건까지 없어지는 것은 아니다.

| 대상 | 공개·사용 방향 | 출시 전 확정할 계약 |
|---|---|---|
| 코어 | 문서 읽기·검증·migration·DSF 출력·컴포넌트 계약 해석·검증 계획 공개 | 정확한 OSS 라이선스·기여 조건 |
| Studio 구현 | 호스팅 제품 중심, 일반 공개 의무 없음 | 제품 이용 조건·기업 소스 계약 |
| 기업 Studio 소스 | 사내 설치·감사·수정 | 접근 주체·재배포·업데이트·지원 범위 |
| SDK·명령 명세 | 공식 확장 통로 제공 | 코어와 결합 범위·버전 지원 |
| 템플릿·출력 runtime | 사용자 앱에 포함 가능해야 함 | 파일별 라이선스·고지·재배포 권리 |
| 사용자 문서·코드 | 사용자 소유·내보내기·계속 사용 | 제3자 권리·기밀 유지 |
| 브랜드 | 코드 공개와 별도 관리 | 상표·로고 사용 지침 |

## 라이선스 후보를 비교하는 기준

MPL 2.0은 파일 단위 copyleft와 배포 시 수정 소스 제공을 비교할 후보다. 다른 파일과 결합한 제품 전체 공개를 자동 요구하는 방식과는 구분한다. 브라우저에 전달되는 코드와 서버에서만 실행되는 코드도 검토 범위가 다르다. [Mozilla 공식 FAQ](https://www.mozilla.org/en-US/MPL/2.0/FAQ/)

AGPL은 네트워크 사용과 수정 소스 제공 의무까지 검토할 후보이므로 Studio 결합·기업 고객 적용 비용을 확인해야 한다. 이 문서는 AGPL이나 MPL을 채택하지 않는다. [AGPL 원문](https://opensource.org/license/agpl-3.0)과 실제 배포 형태를 대조한다. 오픈 소스에 경쟁 용도 금지를 넣어도 여전히 같은 의미의 OSS라고 표현할 수는 없다. 사용 분야 차별 금지 등과 비교해야 한다. [OSI 정의](https://opensource.org/osd)

권고 검토 순서는 공개 코어 MPL 후보 → Studio 비공개/기업 계약 → 사용자 산출물에 포함되는 템플릿·runtime의 허용적 조건이다. 이 조합의 실제 적용은 파일 출처, 기여자 권한, linking·배포 방식 검토 후 결정한다. 기존 LICENSE는 변경하지 않으며 이미 공개한 코드의 권리를 소급 회수하지 않는다.

## 복제 억제와 확장성

API entitlement는 호스팅 자원·기업 기능 사용을 관리한다. 사용자가 이미 적법하게 받은 공개 코어를 로컬에서 실행하는 것을 서버 구독 체크로 봉쇄하지 않는다. Studio 소스 공개 범위, 운영 서비스, 검증된 팩 품질, 브랜드와 고객 지원이 각각 다른 보호 수단이다. 한 라이선스로 모든 복제를 막는다고 약속하지 않는다.

기업 소스 접근은 제품 내부를 고객이 별도 계약으로 수정하는 권리다. 일반 외부 Agent에게 Axiom 서비스 검증기·권한 로직을 수정할 명령을 제공한다는 뜻이 아니다.

## 검토 절차와 실패 처리

공개 전 산출물별 권리표·dependency graph·고지 파일·원본 출처를 검토한다. 권리가 확인되지 않은 asset 또는 템플릿은 해당 배포에서 보류하고 대체를 제안한다. 정확한 라이선스 선택의 승인자는 제품 책임자이며 법률 검토가 필요한 쟁점과 비용을 [선정 기록](../annexes/selection-register.md)에 남긴다. 권리 변경은 사용자 출력의 기존 사용권과 migration에 미치는 영향을 함께 공개한다.

## 결정 추적과 변경 영향

<a id="d03-02"></a>

**D03-02 — 확정 방향:** 문서 읽기·검증·버전·Foundation 출력·컴포넌트 계약 해석·검증 계획 생성은 공개 코어 기본 범위다. 기업 Studio 소스는 사내 설치·감사·수정에 제공하고 제3자 배포·경쟁 서비스는 별도 계약한다. 정확한 공개 코어 라이선스는 비교 후 선정한다.

<a id="d39-04"></a>

**D39-04 — 확정 방향:** 기업 고객의 사내 설치·감사·수정을 허용하고 제3자 배포·경쟁 서비스는 별도 계약 대상으로 둔다. Agent에게 Studio 제품 내부를 수정할 제품 권한을 부여한다는 뜻은 아니다. Studio 구현 복제를 억제하고 공개 코어 수정 내용의 제공 의무를 고려한다. 공개 코어·비공개 제품·브랜드 보호의 효과와 비용을 비교해 조합한다. 특정 라이선스는 아직 선정하지 않았고 이미 공개한 코드의 기존 권리를 소급 변경하지 않는다.
