# BIZ04 · 사용자 조사·제품 검증·고객 피드백

상태: 전체 문서 기준선 검토안 · 목표 Foundation 1.0.0 · 2026-09-12

책임 역할: 사업/마케팅 담당. 이 문서의 설계는 아직 제품 구현·실행 검증 완료를 뜻하지 않는다.

## 무엇을 관찰할 것인가

제품 책임자가 직접 만드는 첫 DS는 전체 흐름의 결함을 찾는 시험이다. 제작자가 기능을 알고 있다는 이유로 초보자도 쉽게 쓸 수 있다고 결론내릴 수 없다. 자가 사용 이후 코드 친숙 디자이너·1인 개발자·작은 제품 팀의 소수 비공개 시험을 진행한다.

시험 과제는 “Button을 만들어 보세요”보다 구체적이어야 한다. 기본 시스템의 색을 바꾸고, Card의 header/body를 구성하고, 키보드로 행동을 시험하고, 자기 React 프로젝트에 설치하고, 사용자 수정본을 보존하며 업그레이드하도록 한다. 설명 없이는 진행하지 못한 지점도 결과로 남긴다.

## 조사 기록의 계약

ResearchSession은 목적, 참가자 유형, 동의 범위, 제품·문서 revision, 과제, 환경, 관찰 시각, 완료/포기/도움 여부, 문제와 원문 발언, 개인정보 제거 상태를 가진다. 인터뷰 발언, 행동 관찰, 제품 사용 로그를 구분한다. 사용자가 원한다고 말한 기능과 실제 막힌 작업은 별도로 분석한다.

| 관찰 | 가능한 원인 | 확인할 다음 행동 |
|---|---|---|
| trait 패널에서 멈춤 | 용어·맥락 과다 | 목적 중심 설정과 예제로 재시험 |
| Canvas는 만족하지만 설치 포기 | 도구·alias·의존성 문제 | doctor와 계획 설명 관찰 |
| AI 결과를 매번 다시 수정 | 컨텍스트·oracle·편집 단위 문제 | 실패 patch와 계약 추적 |
| 업데이트 사용을 피함 | 사용자 수정 손실 우려 | 3-way diff·rollback 과제 |
| Mobile preview를 실제로 오해 | 상태 표시 불충분 | 비교 화면 이해 확인 |

## 우선순위와 피드백 처리

결함은 데이터 손실·권한 우회·계약 위반, 핵심 작업 중단, 빈번한 혼란, 편의 개선 순으로 검토한다. 영향 사용자 수뿐 아니라 복구 가능성·반복 빈도·지원 비용을 기록한다. 사용자가 한 명이어도 파일 손실은 먼저 해결한다. 희귀 취향 요청이 전체 계약을 복잡하게 만드는 경우 커스텀 확장 경계로 해결한다.

각 제안은 issue→관련 결정·문서→수용/대안/보류 이유→변경 revision→재시험 결과를 연결한다. 사용자 원문을 제품의 확정 요구로 자동 승격하지 않는다. 본문의 기존 확정 범위를 바꾸는 경우 GOV01을 적용한다.

## 운영과 검증

초기 유료 분석 서비스를 필수로 도입하지 않는다. 로컬 관찰 기록과 선택한 비식별 진단으로 시작한다. 참가자 모집 수·시험 기간·유료 전환 목표의 정확한 수치는 첫 모집 가능성과 실제 비용을 보고 확정한다. 현재 실적은 없다.

결과 보고서는 성공 사례와 실패 사례, 도움을 받은 조건, 표본의 한계를 함께 보여 준다. 문구를 고친 다음에는 이전에 막힌 과제를 다시 수행하게 하고 관찰 근거로 개선을 판단한다. 고객 문의의 처리·보관·삭제는 [OPS02 · 호스팅·운영·진단·장애·지원](../operations/hosting-observability-and-support.md)와 연결한다.
