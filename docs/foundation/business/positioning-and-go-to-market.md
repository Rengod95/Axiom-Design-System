# BIZ03 · 포지셔닝·마케팅·출시 메시지

상태: 승인된 Foundation 1.0.0 설계 기준선 · 검토 2026-09-13

책임 역할: 사업/마케팅 담당. 이 문서의 설계는 아직 제품 구현·실행 검증 완료를 뜻하지 않는다.

## 어떤 말로 소개할 것인가

대표 소개 문구의 검토안은 “디자인 시스템을 시각적으로 만들고, 실제 프로젝트에서 쓰는 UI 라이브러리로 연결하세요”다. 차별화의 중심은 그림을 코드로 바꾸는 횟수가 아니라, 토큰·컴포넌트 계약·검증·소비 버전을 연결하는 지속적인 관리 경험이다.

| 대상 | 메시지 가설 | 보여 줄 증거 |
|---|---|---|
| 1인 개발자 | 기본 시스템에서 실제 앱까지 시작 비용을 줄인다 | 온보딩→수정→init 화면 |
| 디자이너 | 내부 부위·상태·모션을 직접 편집하고 의미를 보존한다 | Card 편집과 접근성 관계 |
| UX Engineer | 재사용 의무와 플랫폼 차이를 명시한다 | Button/Select 계약·독립 검사 |
| 팀 관리자 | 여러 앱의 변경·의존성을 추적한다 | 버전 고정·doctor·upgrade diff |
| AI 활용 팀 | Agent가 시스템 규칙을 찾아 작업한다 | context 범위·공식 명령·검증 결과 |

## 비교 제품을 설명하는 원칙

UXPin Merge의 코드 컴포넌트 활용, Builder의 등록 컴포넌트·preview 연결, Plasmic의 props/slots 편집, pen.dev의 Agent 친화적인 디자인 문서는 참고 패턴이다. Axiom의 초기 제품은 ADS로 시스템 자체를 제작하고 타깃별 결과를 검증하는 데 집중한다. 비교 제품이 디자인 시스템을 전혀 다루지 않는다거나 CMS만 한다고 단정하지 않는다. 기술 비교 근거는 [레퍼런스 기록](../annexes/technology-and-references.md)에 둔다.

초기 외부 React 역수입 제외를 숨기고 “모든 코드를 자유롭게 왕복 편집”이라고 홍보하지 않는다. Web/Mobile의 공유 목적과 타깃별 appearance를 “모든 플랫폼에서 픽셀이 같다”로 바꾸지 않는다.

## 공개 콘텐츠와 유입 실험

첫 자료는 실제 설치 가능한 작은 예제, 세 컴포넌트 제작 과정, 기존 파일을 보존한 업그레이드 사례다. 한국어·영어로 동일한 제품 범위와 제한을 전달한다. 디자인·프론트엔드 커뮤니티, 공개 코어 문서, 짧은 제작 영상은 소규모 시험 채널 후보다. 콘텐츠 제작과 개별 연락·발송은 별도 실제 작업의 승인 범위에서 수행한다.

유입→첫 편집→검증→실제 설치→재방문의 전환을 비교한다. 클릭률이 높더라도 사용자가 제품 목적을 오해하거나 실제 설치를 못하면 메시지를 수정한다. 현재 채널 효과·고객 수·매출을 추정 실적으로 기록하지 않는다.

## 주장 검토와 유지보수

출시 페이지의 지원 badge는 release profile과 evidence로 추적한다. “검증됨”은 대상 버전·환경·수동 범위에 링크하고, 계획·preview·부분 출력은 별도 문구를 쓴다. 고객 사례 수치에는 측정 조건과 허락을 확인한다. 기술·출시 범위가 바뀌면 소개 문구·가격 페이지·온보딩·문서의 변경 목록을 함께 검토한다.

대표 메시지의 선택은 제품 책임자가 비공개 시험 결과를 보고 확정한다. 기술 문서가 완성됐다는 이유로 공개 런칭 카피를 확정된 제품 성능처럼 게시하지 않는다.
