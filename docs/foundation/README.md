# Axiom Foundation 1.0.0 문서 구조 검토

2026-09-12 · **제품 방향 확정 / 문서 인덱스 제안 / 인덱스 컨펌 대기**

이번 사용자 확인으로 129개 원 답변, 14개 보충 답변, 조합·위임안과 조건부 선정 방향을 확정했습니다. [확정 기록](../decisions/axiom-foundation-direction-approval.md)에 범위를 남겼습니다. **지금 확인할 것은 전체 문서를 어떤 구조·책임·순서·완료 기준으로 만들 것인가입니다.** 56개 본문은 아직 작성하지 않았습니다.

Foundation 1.0.0은 토큰만을 뜻하는 DSF와 다릅니다. 제품을 왜 만드는지, 사용자가 무엇을 끝내는지, 무엇을 어떤 계약으로 저장하는지, 어떻게 검증·전달·운영하고 수익을 만드는지를 연결한 제품 전체의 기준 문서 묶음입니다.

## 제안하는 구조

**12개 분야, 56개 문서**로 나눕니다. 문서 수는 책의 권수나 구현 모듈 수가 아닙니다. 서로 다른 변경 이유를 가진 규칙의 관리 단위입니다. 짧은 주제는 짧게 쓰고, 상세한 규칙표·카탈로그는 소유 문서에 연결한 부록으로 관리합니다. 1인 개발자가 아래 책임 역할을 겸합니다.

| 분야 | 문서 수 | 이 분야를 읽으면 판단할 수 있는 것 |
| --- | ---: | --- |
| GOV · 결정·문서 운영 | 3 | 어느 결정이 기준이며, 용어·버전·변경을 어떻게 관리하는가 |
| PRD · 제품 기획 | 3 | 누구의 어떤 문제를 해결하며, 사용자가 어디까지 끝내야 하는가 |
| BIZ · 사업·마케팅·시장 검증 | 4 | 무엇을 무료/유료로 제공하고, 권리·원가·고객·메시지를 어떻게 검증하는가 |
| BRD · 브랜드·자산 | 2 | 브랜드를 DS와 분리 관리하면서 실제 디자인에 어떻게 결합하는가 |
| SYN · ADS·DSF·표준 | 4 | 문서·토큰·테마·정책·참조·입출력의 의미가 무엇인가 |
| CMP · 컴포넌트 계약 | 11 | 부품·값·상태·동작·접근성·모션·확장이 어떤 약속을 갖는가 |
| UX · 디자인·UX/UI | 8 | Canvas와 Inspector에서 그 약속을 어떻게 쉽고 풍부하게 편집하는가 |
| ARC · 시스템 아키텍처 | 7 | 명령·저장·Host·API·협업·권한·모듈이 어떻게 연결되는가 |
| AI · 작성·코드 실현 | 2 | AI가 무엇을 읽고 수정하며, 생성 결과를 누가 어떻게 검증하는가 |
| DLV · 플랫폼 출력·설치 | 4 | 사용자 소유 코드를 어떻게 만들고 설치·업그레이드·복구하는가 |
| QAL · 품질·검증·출시 | 4 | 무엇을 검사하고 어떤 증거가 있어야 정식 지원이라고 말하는가 |
| OPS · 개발·보안·운영 | 4 | 계속 개발하고 배포·관찰·복구·지원할 수 있는가 |
| **합계** | **56** | **제품 목적에서 유지보수까지 연결** |

전체 경로와 문서별 책임·선행 자료·완료 기준은 [상세 인덱스](document-index.md)에 있습니다. D01–D39의 129개 세부 답변은 [결정 연결표](decision-coverage.md)에서 주 소유 문서 하나씩으로 연결했습니다.

## 규칙이 여러 문서에서 달라지지 않게 한다

예를 들어 “Toast가 사라지는 동안 새 요청이 오면 어떻게 되는가”는 다음처럼 나눕니다.

- CMP04와 CMP09는 상태·요청·모션의 의미와 중단 규칙을 정의합니다.
- UX06은 그 규칙을 사용자가 시연하고 편집하는 방법을 설명합니다.
- DLV01은 각 타깃의 실제 구현 방식과 차이를 관리합니다.
- QAL01·QAL02는 검사 요구와 현재 코드의 검증 증거를 관리합니다.

UX 문서가 별도의 모션 규칙을 만들거나, 플랫폼 구현이 편의를 위해 공통 계약을 조용히 바꾸지 않습니다. 새로운 사실이 드러나면 원 소유 문서와 관련 문서를 함께 수정합니다.

이 구조는 코드 패키지나 배포 서버를 56개로 만들겠다는 뜻도 아닙니다. 실제 모듈과 기술은 ARC02에서 책임·결합도·운영비를 기준으로 설계합니다.

## 읽는 순서와 작성하는 순서

처음 제품을 이해할 때는 **PRD01 목적 → PRD02 전체 사용자 흐름 → ARC01 시스템 지도 → SYN/CMP의 핵심 개념 → UX 편집 → DLV 전달 → QAL/OPS 검증·운영** 순서가 좋습니다. 사업·마케팅 검토에서는 PRD 뒤에 BIZ·BRD를 읽습니다.

작성은 의존성에 맞춰 진행합니다. 제품·사업 원칙과 공통 용어부터 시작하고, 문법·컴포넌트 계약과 편집 시나리오를 맞춰 본 다음 시스템·AI·전달·검증·운영 문서를 연결합니다. 마지막에는 Button·Card·Toast와 복합 입력/overlay 사례를 전체 흐름에 대입해 충돌을 찾습니다. [지속 개발 방향](development-direction.md)에 단계별 산출물과 확인 기준을 정리했습니다.

## 문서의 완료와 제품의 완료를 나눈다

문서 완료는 용어·규칙·관계·필드·예제·오류·검증 계획·변경 영향이 일관되게 설명되어 **구현자가 무엇을 만들지 판단할 수 있는 상태**입니다. 빈 heading, 링크 목록, 모호한 ‘추후 검토’만으로 완료하지 않습니다.

제품 완료는 그 문서에 따라 실제 구현을 실행하고, 약속한 카탈로그·타깃·환경에서 검증을 통과한 상태입니다. 문서가 1.0.0이라고 프로그램도 1.0.0으로 출시할 수 있는 것은 아닙니다.

자체 표준의 이점·성능·정확한 운영 원가처럼 실제 실행이 필요한 항목은 먼저 후보·판정 기준·검증 계획·실패 시 대안을 명시합니다. 아직 없는 실행 결과를 문서 승인 조건으로 요구하지 않습니다. 동시에 기술·라이선스가 미선정인 것을 ‘선정 완료’로 바꾸지도 않습니다.

## 이번 컨펌 대상

1. 위 12개 분야·56개 문서의 구분과 소유 경계.
2. D01–D39를 빠짐없이 연결한 범위와 부록 관리 방식.
3. 문서 작성 순서, 설명·사례 중심의 깊이, 완료·변경 기준.
4. 문서 확정 이후의 구현 순서와 전체 출시 조건을 유지하는 방식.

이 인덱스 확인은 전체 상세 명세나 특정 Canvas 엔진·토큰 표준·라이선스의 자동 채택이 아닙니다. 확인 후 전체 문서를 작성하고 문서 기준선 확인을 받은 다음 실제 제품 코드를 구현합니다.

원격 정리 PR [#24](https://github.com/Rengod95/Axiom-Design-System/pull/24)는 병합됐으며 고정 참조 구현은 그대로 보존됩니다. 문서 인덱스 제안은 그 정리와 별도의 확인 대상입니다.
