# Foundation 문서화와 지속 개발 방향

상태: **인덱스와 함께 확인받는 개발 방향 제안** \
목표 기준선: Foundation 1.0.0 \
연결: [검토 시작](README.md) · [문서별 범위](document-index.md) · [결정 연결표](decision-coverage.md)

## 1. 현재 허용된 작업과 확인 지점

| 단계 | 현재 상태 | 통과 조건 | 이후 허용되는 작업 |
| --- | --- | --- | --- |
| 방향 결정 | 사용자 확인 완료 | 통합 해석·위임안·조건부 선택 절차 기록 | 문서 인덱스와 개발 방향 설계 |
| 인덱스·개발 방향 | **이번 컨펌 대상** | 범위·책임·의존 순서·완료 기준 확인 | 전체 상세 문서 작성 |
| 전체 문서 기준선 | 미작성 | 56개 문서와 필요한 부록의 완결성·일관성 확인 및 사용자 컨펌 | 구현 시작을 위한 모듈·검사 구성 |
| 제품 구현 | 미시작 | 승인 문서의 계약을 코드·검증으로 실현 | 내부 알파·실제 타깃 검증 |
| 정식 출시 | 미완료 | 약속한 전체 카탈로그·필수 타깃·환경의 실제 증거 | 정식 지원 표시와 배포 |

현재 필요한 것은 두 번째 단계의 구체안입니다. 인덱스 승인 전에 56개 빈 파일을 만들거나 본문 작성 완료로 표시하지 않습니다. 문서 확정 전 Studio·Host·새 schema/validator 같은 제품 구현을 시작하지 않습니다.

## 2. 하나의 문서를 어떻게 작성할 것인가

처음에는 이 문서가 해결하는 사용자 문제와 일반적인 사례부터 설명합니다. 그다음 핵심 개념을 영어 원어와 한국어 설명으로 소개하고, 관계·규칙·오류·경계를 구체화합니다. 기술 명세가 필요한 부분에는 필드표·상태도·계약 예제를 제공하되, 그 이유를 이해할 수 있는 설명과 연결합니다.

공통으로 갖출 내용은 다음과 같습니다.

1. 목적과 적용 범위, 연결된 사용자 결정 ID.
2. 용어·개념과 대표 사용자 시나리오.
3. 자신이 소유하는 규칙, 다른 문서에서 가져오는 규칙.
4. 정상 흐름과 실패·취소·충돌·복구 사례.
5. 구체적인 필드·관계·행동·입출력 또는 사업 가설.
6. 검증 방법·증거 책임·아직 검증하지 않은 범위.
7. 바뀌면 영향을 받는 문서·산출물·호환성·사용자 작업.

모든 문서에 같은 길이를 강제하지 않습니다. 예를 들어 브랜드 지침은 설명·예제가 중심이고 상태 계약은 전이·요청·취소의 정밀한 표가 필요합니다. 사업 문서에는 코드 필드 대신 대상·가치·비용·관찰 방법·판단 시점을 둡니다.

### 사례의 일관성

Button은 조작·비활성·포커스의 기본 계약을, Card는 기본 표면에 기능을 조합하는 방식을, Toast는 수명·공동 호스트·모션을 설명하는 공통 사례로 사용합니다. 이 세 사례만으로 전체 시스템을 검증했다고 보지 않습니다. Select/ComboBox와 Dialog 등은 복합 입력·선택·외부 제어·overlay·접근성 관계를 확인하는 추가 사례로 사용합니다.

가격 계산·결제 성공·업무 권한 같은 비즈니스 규칙은 컴포넌트 계약에 포함하지 않습니다. 테스트와 문서 예시도 이 경계를 지킵니다.

## 3. 전체 문서를 만드는 순서

아래 묶음은 작업 계획입니다. 실제 문서의 의존 순서는 [manifest](document-manifest.json)의 `upstreamDocumentIds`와 일치시킵니다. 같은 문서를 초안과 통합 검토에서 다시 읽는 것은 새로운 중복 문서를 작성한다는 뜻이 아닙니다.

| 작성 묶음 | 먼저 정리할 내용 | 다음 작업에 넘길 산출물 |
| --- | --- | --- |
| A · 제품과 운영 원칙 | GOV, PRD, BIZ, BRD | 사용자·문제·출시 범위·권리·비용 가설·용어·자산 경계 |
| B · 문법과 컴포넌트 의미 | SYN, CMP | 문서/ID/토큰/테마·컴포넌트 정의·상태/행동/접근성/모션·확장 계약 |
| C · 사용자 경험과 시스템 구조 | UX, ARC | 토큰/컴포넌트 편집 흐름·Canvas 조작·명령/저장/Host/API·모듈 경계 |
| D · AI·출력·검증 | AI, DLV, QAL | 후보 생성·독립 판정·실제 타깃/의존성·init/doctor·사용자 수정·출시 증거 |
| E · 지속 운영과 통합 정합화 | OPS와 전체 교차 검토 | 배포/복구/보안/지원 절차, 변경 영향, 전체 인수 시나리오, 문서 기준선 |

사업·UX 검토에서 계약이 바뀌면 B의 소유 문서에 반영하고 연결된 문서를 갱신합니다. 앞 묶음을 승인했다는 이유만으로 잘못된 규칙을 고칠 수 없게 만들지 않습니다. 다만 이미 확인한 제품 방향을 바꾸는 경우에는 변경 이유와 영향을 제시해 확인받습니다.

문서 기준선 확인 시에는 56개 파일 수만 검사하지 않습니다. 모든 사용자 결정이 실제 본문의 규칙이나 조건으로 반영되었는지, 예제·설계표·용어가 일치하는지, 미결정에 책임·조건·처리 시점이 있는지를 확인합니다.

## 4. 상세 문서에서 결정하거나 증거를 준비할 사항

| 항목 | 이미 확정한 방향 | 남은 구체화 | 늦어도 확인해야 할 시점 |
| --- | --- | --- | --- |
| 토큰 표준 | 이점 있는 자체 표준 허용, 이점 없으면 DTCG 전체 지원 | 기준 판본·후보 의미·매핑·렌더링/보존 비교·전환 전략 | SYN 상세 명세의 후보와 판단 기준은 문서 확인 전, 실증은 표준 안정화·출시 전 |
| Canvas·레이아웃·텍스트 기술 | 풍부한 컴포넌트 편집, 엔진은 제품 목적을 따름 | 렌더/편집/텍스트/레이아웃 분담과 교체 경계, 실제 도구 선정 근거 | 관련 구현 착수 전. 미선정 엔진을 이미 채택한 것처럼 쓰지 않음 |
| 타깃·스타일·기반 | React/RN/Swift/Android 요구, 실제 성립하는 조합·대응 기반 명시 | native toolkit·CSS-in-JS 구현/버전·SSR/RSC·환경·검증 표 | 출력 profile 구현 전; 전체 지원 증거는 출시 전 |
| 카탈로그 | 초기 기본군의 편집·출력·검증 범위 유지 | 중복·Part·template·고유 component 구분과 유형별 의무 | PRD03/CMP02 상세 문서 확인 전 |
| 공개·기업·산출물 권리 | 공개 코어와 Studio 구현·기업 소스·사용자 코드의 구별 | 정확한 라이선스, 제3자·템플릿·생성 런타임 권리 | 외부 코드/템플릿 배포나 기업 계약 체결 전 |
| AI 연결 | 사용자 키/지원 연결, 내부 AI 및 공식 API/MCP | 실제 인증 방법·지원 공급자·오프라인 내부 연결·비용 한도 | 연결 기능 구현·지원 약속 전 |
| 성능·운영 원가 | 대표 규모·비용을 측정해 판단 | 데이터셋/기준 장비·작업별 측정법·예산/중단 조건 | 계획은 문서 확인 전, 실제 수치와 통과는 구현·출시 단계 |
| 사업·메시지 | 개인 무료 가치·편집 좌석·자원 비용·검증할 유료 가치 | 가격 수치·유료 묶음·소개 메시지의 실측 | 공개 요금·메시지 확정 전 |

미결정 항목은 `무엇 / 왜 아직 미정 / 기준안·대안 / 책임 / 필요 증거 / 처리 시점 / 실패 시 대안 / 영향 문서`로 관리합니다. 실행 증거가 없다는 이유로 문서 작성을 멈추지 않으며, 코드에 영향을 주는 계약 자체가 비어 있는데 문서를 완료했다고 선언하지도 않습니다.

자체 표준을 후보로 상세 설계할 수는 있지만, 우위를 실증하기 전에는 ‘DTCG보다 낫다’거나 출시 가능한 새 표준으로 발표하지 않습니다. 검증 결과에 따라 기존 선택을 바꾸면 ADR과 관련 명세·migration·지원표를 함께 갱신합니다.

## 5. 문서가 확인된 뒤의 구현 순서

1인 개발에서는 공통 계약을 관리할 수 있는 최소 기반을 만든 다음, 전체 사용자 작업이 이어지는 단위로 구현합니다. 아래 순서는 내부 개발 계획이며 정식 출시의 필수 기능을 줄이는 합의가 아닙니다.

| 내부 구현 단계 | 구현 단위 | 확인할 사용자 결과 |
| --- | --- | --- |
| I0 · 기준과 작업 기반 | 승인된 모듈/언어/의존성·문서/계약 추적·검사 환경 | 변경의 권위와 검사 방법을 재현할 수 있음 |
| I1 · Foundation 편집 전체 흐름 | 문서/ID·토큰/테마·명령/revision/Undo·저장/복구·기본 GUI | 토큰 기반을 시각적으로 만들고 변경·저장·다시 열 수 있음 |
| I2 · 컴포넌트 정의와 편집 | Part/slot·값/이벤트·상태·외형·Canvas/Inspector·접근성/모션 | Button/Card/Toast와 복합 입력 예제를 정의·수정·시연할 수 있음 |
| I3 · AI와 검증된 실현 | 공통 작성 API·내장/외부 AI·후보 생성·고정 oracle·실제 타깃 실행 | 같은 정의로 후보를 만들고 실패 원인과 검증 상태를 확인할 수 있음 |
| I4 · 사용자 프로젝트 적용 | 사용자 소유 패키지·init/doctor·기반/alias·diff·업그레이드/rollback | 실제 React/RN 및 필수 native 환경에 설치하고 변경을 추적할 수 있음 |
| I5 · 전체 약속 완성 | 전체 카탈로그/타깃/스타일·접근성/IME·오프라인·보안·성능 | 필수 지원표를 전체 증거와 연결해 정식 출시를 판단할 수 있음 |

토큰 편집을 먼저 안정화하되 컴포넌트 편집·native 출력·키프레임을 초기 제품에서 임의 제외하지 않습니다. 실시간 협업은 변경·충돌·Undo 구조를 처음부터 고려하고 실제 공동 편집 서비스는 후속으로 둡니다. CMS 범위는 Builder의 이름만 바꿔 끌어오지 않습니다.

초기 코드 기반은 교체 가능한 경계를 가진 단일 개발 저장소를 우선 검토합니다. 필요한 이유가 확인되지 않은 마이크로서비스, 모든 기능의 플러그인화, 별도 자체 렌더 엔진을 선행하지 않습니다. 공개 코어·유료 서비스 경계는 책임과 배포 권리를 기준으로 설계합니다.

## 6. 이후 변경이 들어올 때의 유지보수 흐름

새 요구는 먼저 어떤 사용자 문제를 해결하는지와 영향을 받는 D결정·문서 ID를 찾습니다. 원 소유 문서에서 의미를 수정하고, 소비하는 UX·타깃·검증·운영 문서가 함께 바뀌는지 확인합니다. 그다음 계약/fixture·구현·회귀 검사·배포·사용자 프로젝트 영향을 처리합니다.

예를 들어 Card의 새로운 variant는 CMP10과 UX06, 출력 영향이 있는 DLV01/QAL02를 확인합니다. 같은 Card의 공개 값이나 필수 동작을 바꾸면 CMP03/CMP04/GOV03까지 포함합니다. 새 타깃을 추가하면 원 소유 계약을 복제하지 않고 DLV01의 profile과 실제 검사·지원표를 추가합니다.

| 변경 종류 | 기본 확인 수준 |
| --- | --- |
| 오탈자·동일 의미의 설명 개선 | 소유 문서 수정, 링크·용어 확인 |
| 공개 필드·의무·지원 범위 변경 | 영향 문서·호환성·증거·migration과 ADR 검토 |
| 제품 범위·권리·가격·기본 사용자 경험 변경 | 사용자에게 구체 변경안과 영향을 제시해 확인 |
| 구현 버그 수정 | 승인 계약 안에서 수정하고 해당 회귀 증거 갱신 |
| 검증 실패로 계약을 바꿔야 하는 경우 | 실패 구현과 기준 변경을 구별해 별도 확인 |

문서 상태는 `초안 → 검토 → 확인 → 대체됨/폐기됨`으로 관리하고, 증거는 별도로 `미실행 / 통과 / 실패 / 오래됨`을 기록합니다. Foundation 버전은 문서 묶음의 기준선, ADS 판본은 파일 호환성, 출력 UI 패키지 버전은 소비 프로젝트 업그레이드 단위입니다. 이 숫자를 하나로 자동 동기화하지 않습니다.

## 7. 기존 자료의 활용과 산출물 보관

이전 조사 문서·컴포넌트 사전·정적 예제·실험은 재사용 근거입니다. 각 문서에 필요한 부분을 가져올 때 현재 결정과 대조하고 원 출처·적용 한계·확인 시점을 남깁니다. 과거 설명 전체를 새 규범으로 복사하지 않습니다.

이전 실행 구현은 [고정 참조 커밋](https://github.com/Rengod95/Axiom-Design-System/commit/1b7bd6843ac638fac89da424637afa755d076144)에서 찾습니다. 코드·fixture의 당시 성공 결과와 신규 계약의 통과 결과를 분리합니다. 정리된 기존 패키지를 다음 구현의 기본 구조로 복원하지 않습니다.

인덱스는 문서 ID·위치·소유·선행 관계·결정 연결을 관리하고, 각 문서는 자신의 규칙을 관리합니다. 부록·ADR·검증 증거에는 소유 문서와 revision을 연결합니다. 향후 필요한 문서가 생기면 기존 소유 문서에 포함할지 독립 문서로 분리할지 변경 이유를 기록하고 인덱스를 갱신합니다.
