# Gate A N16-N24 design

**Status:** APPROVED CONTINUATION \
**Date:** 2026-09-02 \
**Scope:** Motion, behavior, reference types, Recipe authoring, normalization,
and the Button vertical conformance fixture

## Goal

Implement N16 through N24 on the reconciled N0-N15 baseline without allowing
authoring convenience, provider details, or compiler behavior to redefine a
normalized contract. Each N item remains a focused review boundary. Independent
contract work may be prepared in parallel, but integration follows the
normative dependency order and is reconciled before each pull request.

All newly written or materially modified TypeScript callables follow the
repository English TSDoc rule introduced with this work.

## Authority and dependency design

The authority order remains ADR -> SSOT -> schema and registry -> fixtures ->
generated/reference TypeScript -> implementation. The integration order is:

```text
N16 Motion IR ---------+
                       +--> N18 reference types --> N19 Recipe Kernel
N17 Behavior schemas --+                              |
                                                      v
                              N20 authoring --> N21 validation --> N22 normalizer
                                                                        |
                              N23 Motion authoring/normalizer ------------+
                                                                        |
                                                                        v
                                                           N24 Button fixture
```

N16 and N17 may be implemented in parallel and reconciled in that order. N19
structural work may be prepared independently, but it is complete only after
N18 fixes the shared serializable types. N20, N21, and N22 share the authored
declaration model and therefore integrate sequentially. N23 and its Recipe/Slot
integration are complete after N22; N24 remains the next downstream vertical
fixture.

## Contract decisions

### Motion IR

- A normalized Motion track includes required `allowDiscrete: boolean`.
  `false` is the ordinary value; `true` preserves the explicit authoring opt-in
  required for a discrete property so later backends can audit the decision.
- Spring literal bounds are schema-owned: `bounce` is in `[0, 1]`, while
  `stiffness`, `damping`, and `mass` are finite numbers greater than zero. No
  arbitrary maximum or new registry is invented.
- `recipeId` is an explicit Motion authoring field. It is never inferred from a
  dotted Motion ID. `profileInputDigest` and `conditionRegistryDigest` are
  supplied by the normalizer context from exact validated inputs, not authored.
- Two shorthand keyframes normalize to offsets `0` and `1`. Three or more
  keyframes require explicit offsets until an interpolation policy is governed.
- CSS properties with `motion: unknown` produce a warning and remain subject to
  backend validation. Backend transition support (`AXM1006`) and provider
  lifecycle capability (`AXM1009`) remain N31/N33 responsibilities.
- Reduced-motion identities remain distinct:
  `preference.reducedMotion` Condition -> `reducedMotion` IR policy ->
  `motionSuppressed` lifecycle observation.

### Behavioral Criteria

N17 defines two closed, provider-neutral source/profile data schemas and
structural fixtures. The Behavior Projection schema and its coverage rules are
owned by N33 with the React Aria projection boundary; N17 does not predeclare
provider-observation mappings.
It does not install React Aria or claim a current provider baseline. ADR-0005
clarifies that N32 pins provider packages, captures official evidence, and
emits executable Button/Select/Dialog profiles.

The source-manifest digest is reproducible:

```text
manifestDigest = sha256(canonical JSON of the manifest without manifestDigest)
```

Evidence records use the initial retrieval policy `pinned-artifact` and name a
repository-relative artifact path. N17 fixtures use visibly synthetic package,
integrity, evidence, and digest values. `providerObservation` and
`canonicalProjection` remain opaque serializable strings at this schema stage;
N32 owns real mappings and cross-evidence coverage.

### Reference TypeScript surface

N18 generates or references types subordinate to the completed schemas and
registries. Generated files identify source identity, generator version, schema
or profile version, and canonical input digest, and are drift-checked. Static
types improve authoring but never replace runtime registry, grammar, Token, or
semantic validation.

`@axiom/spec-tooling` owns the build-time reference-type generator. The
`contracts:generate` command writes generated/reference contracts to the public
`src/generated/` destinations of `@axiom/condition-registry`,
`@axiom/motion-schema`, and `@axiom/behavior-contracts`; `contracts:check`
regenerates in a clean temporary location and rejects drift. No handwritten
parallel public contract is authoritative.

The packages are:

- `@axiom/condition-registry` for generated State and Condition identities;
- `@axiom/motion-schema` for Motion contracts, later extended by N23;
- `@axiom/behavior-contracts` for source/profile contracts;
- existing Token and CSS-profile owners for their generated identities.

### Recipe and Appearance

`@axiom/recipe-kernel` is generic over `TStyle`. It owns only JSON-safe
structure, literal Slot/Variant inference, defaults, source order, State and
Condition separation, compounds, and structural diagnostics.

`@axiom/appearance-authoring` adds CSS-aware authoring values and
`defineRecipe`. N20 owns `token`, literal CSS, CSS templates, and restricted
Token negation representations, but deliberately does not claim full Token or
grammar validity. N21 validates every declaration against explicit effective
property, resolved Token, serializer, binding, and projector inputs. The
machine-readable projector identity `css.shadow.v1` is authoritative; the stale
annex spelling is corrected.

`@axiom/appearance-normalizer` emits the exact N15 `CSSAppearanceIR` and a
separate deterministic collision trace validated by the closed
`spec/css/collision-trace.schema.json` and its fixture suite. The closed IR
schema does not gain diagnostics. Diagnostics reference trace IDs through
schema-allowed `details`; the trace carries both declaration origins and
affected-property provenance.
Until a separately governed package split, the generated serializable
`CSSAppearanceIR` and `CollisionTrace` types remain in `@axiom/motion-schema`.
That shared carrier is type-only and grants no Appearance-normalization
ownership to Motion.
The current `profileInputDigest` meaning remains the profile manifest's
`webrefInputDigest` until a separately governed migration changes it.

### Motion authoring and Button vertical fixture

N23 extends `@axiom/motion-schema` with literal-preserving `defineMotion` and a
deterministic normalizer. It authenticates an explicit detached N22
`CSSAppearanceIR` through a canonical digest and validates its matching
profile, Recipe, and Slot; it does not read repository files or import
Appearance-normalizer, runtime, or provider code.

N24 proves that one authored Button produces an instance of the existing
`css-appearance-ir` positive contract, the existing `motion-ir` positive
contract, and the collision-trace schema, plus a package-local golden output.
It proves deterministic serialization and collision evidence, but is a
Foundation fixture rather than a React component or browser-conformance claim.
Provider behavior, DOM, accessibility-tree, and manual-AT evidence remain
N32-N35.

## Pull request and verification design

Each N item receives its own commit and stacked pull request. Before the next
item is integrated, the exact head must pass its focused tests plus:

```bash
pnpm check
pnpm test
pnpm build
git diff --check
```

Stacked pull requests are merged in N order. After each merge, the next pull
request must be retargeted to `main`, synchronized with the merge commit, and
revalidated before merge. This requirement prevents a branch-only merge from
being mistaken for a `main` integration.
