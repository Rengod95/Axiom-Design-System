# ADR-0014 — Studio authoring and target delivery

Status: ACCEPTED for continued implementation

Date: 2026-09-13. Owner: product owner; executor: Codex. The owner explicitly requested PR #28 merge and uninterrupted continuation through the editor and target implementation. PR #28 merged at `6cdac6a9635fd481f298ae87be82c4c7365bbf7f` after exact-head Windows/Ubuntu checks passed.

## User task and progression

Implement the OPS04 vertical flow: start a local design system, edit shared tokens and themes, select and edit Button/Card/Toast parts, compare Web/Mobile designs, review and persist through the existing command boundary, then export user-owned target source and inspect upgrade differences. This continues I2–I4 and the first I5 target generators while preserving every remaining Foundation obligation. The full catalog, all token-standard operations, AI realization, native execution evidence and release acceptance are not implied by this flow. I1's local storage and review path is sufficient for these local documents; external library resolution, schema migrations, compaction and full offline storage remain explicit work.

## Source and command contract

Add the opt-in `foundation-studio` validation policy and `ads-studio` import format, stronger than `foundation-domain`. Documents use schemaVersion `1.0.0` with an explicit `studioProfile: { id: "axiom.studio", version: "0.1.0" }`. Only foundation, component and design documents with this supported profile are executable by this increment. Existing envelopes retain their policy; source repair/update cannot weaken a previously adopted policy. The core checks document semantics and the complete project graph when staging, applying, deleting and undoing. A browser-only preflight never substitutes for those checks.

GUI mutations use existing `project.create`, source-preserving `document.import` review/update, `transaction.review/apply/undo/redo`. New editor projection/edit helpers prepare immutable source updates and impact descriptions; they do not write storage or bypass review. Document-specific named catalog commands remain separately tracked until implemented. A private authoring-state query exposes only the current principal's candidate summaries and applicable Undo/redo handles, under current read authority; it does not expose approval tokens. Stable retry envelopes survive response failures. Draft buffer, captured source, proposed candidate, adopted revision and transient preview remain distinct.

## Foundation authoring profile

Retain the catalog Token fields and use `typeRef: { id: <DTCG type name> }`. Token.value is exactly `{ literal: <DTCG value> }` or `{ ref: { id: <stable token ID>, expectedKind: "token" } }`. Aliases resolve inside the current Foundation, with missing/cyclic/mismatched-type diagnostics. Renaming retains identity; resolved values are derived and never replace stored aliases. Inspect the thirteen DTCG 2025.10 value types and declared color spaces; rendering/target capability is narrower and must reject unsupported conversions explicitly.

ThemeAxis gains optional `overrides: { <context>: { <token ID>: <Token.value> } }`. Foundation gains `resolutionOrder: <axis ID>[]`, listing every axis exactly once. Resolve context from a named ThemeSet, explicit context overrides and axis defaults; reject unknown axes/contexts and incomplete selection. Apply chosen override maps in the explicit resolution order, then resolve aliases with type checking and provenance. Axis scopes must refer to the current Foundation. ThemeSet.resolutionProfile pins `{ id: "axiom.resolver.explicit-order", expectedKind: "resolutionProfile", version: "1.0.0" }`. This is a named ADS authoring resolver, not execution of arbitrary DTCG Resolver documents.

The SYN01 comparison baseline remains [DTCG Format](https://www.designtokens.org/TR/2025.10/format/), [Resolver](https://www.designtokens.org/TR/2025.10/resolver/) and [Color](https://www.designtokens.org/TR/2025.10/color/). ADS identity/graph authoring is a bounded B experiment. Preserve original exchange bytes and opaque metadata/extensions; report unsupported group inheritance, property references or resolver features rather than flattening them silently. SEL01 remains incomplete until the full comparison corpus and four-target evidence exist. A color picker cannot narrow the source contract; detailed JSON editing and failed-source capture stay available.

## Components, designs and execution

ComponentDefinition and DesignDefinition retain their Foundation fields. This increment pins builtin archetype contracts for command Button, content Card and controlled notification Toast; unknown archetype/version/contract mutations fail executable-profile validation instead of becoming generic views. Components have stable Part/Slot/value/event IDs. Public values belong to the consumer; activation and closeRequest express UI intent. A plain Card is a content container with a required body, not an interactive control. Toast's consumer open, close request, runtime presence and motion progress are separate; no automatic timeout is enabled by default.

Designs reference their component and select Web or Mobile. Supported PartNodeMapping, stack layout, bounded visual declarations, variant/state rules and token bindings are explicitly validated. Precedence is base, matching variant/state and explicit priority; equal-precedence conflicting declarations are errors. Component preview sample content is editable authoring data, not a business rule. Web/Mobile may vary layout, spacing and appearance while retaining the same public meaning. Pinned profiles own accessible native controls, reading order, minimum action sizes, reduced motion and bounded Toast cleanup; unsupported obligations prevent target certification. External library version resolution is not inferred from these builtin pins.

## Module and dependency ownership

Keep browser-neutral token/component semantic helpers inside the existing ads-core logical core. Add `modules/target-packs` for fixed-snapshot planning, source generation, archive and three-way comparison, with no UI, Node or storage dependency. Add `apps/studio` for React views/controllers and `apps/delivery` for bounded filesystem delivery operations. Studio depends only on public core/browser-store/target-packs barrels. Delivery depends on public core/local-store/target-packs barrels. Core/storage never import Studio or target packs.

Pin React and React DOM **19.3.0** (MIT) for the actual DOM editor and React consumer checks, with matching **19.3.0** type packages. Pin esbuild **0.28.2** (MIT) as build/test tooling. Existing hash and test dependencies remain narrowly owned. Build browser assets locally with a deterministic bundle; no remote CDN, runtime source evaluation or imported user code executes in Studio. This is the SEL02 React/DOM candidate with actual workload evidence; full Canvas/text-engine selection remains open. Target dependency/toolchain pins and licenses must be recorded with their generated manifests and verification evidence before adoption.

## Delivery and verification boundary

Generate deterministic user-owned React/CSS, React Native, SwiftUI and Compose source packages from a validated fixed snapshot and context. Manifest pins source revision/digest, generator and target profiles, supported capabilities, file digests, conversion policy and evidence scope. React browser/SSR and RN compiler/bundler checks are distinct from native device execution. Windows cannot establish Apple SwiftUI execution; native toolchain availability must be observed and recorded. Never label source generation as installed or platform-verified.

The first target mapping supports explicit sRGB and declared logical dimension conversion for the selected property profile; other colors/units/types remain preserved in ADS but fail unsupported usage before output. Do not omit unknown required properties or dependencies. Browser export uses a downloadable source archive; Node delivery checks exact file inventories and paths. Fresh installs never overwrite existing user files. Three-way plans distinguish immutable generated baseline, current user bytes and new generated bytes. User-only edits are preserved, competing changes conflict, stale plans fail, and rollback checks intervening edits. No automatic package install, registry publication or remote deployment occurs as a side effect of source export.

Required evidence includes core positive/negative fixtures; invalid token/type/alias/theme and component obligations; source policy inheritance and one-Undo review; real Studio keyboard/selection/transient-preview/ko-en/error/restart flows; emitted target source consumed independently; source escaping, deterministic archive and digest checks; three-way user edits/conflicts/stale/rollback; import graph and archive leak checks. Existing Windows/Ubuntu Foundation, frozen-reference, kernel and real-browser gates remain mandatory. Evidence records implementation, execution and unverified scope separately.

## Bounded implementation decisions

Studio permits 64 components, 32 named ThemeSets and 128 rules per design under existing document/batch limits; graph evaluation reuses context resolutions. Additive Design.foundationRef checks local kind and optional revision pins. Part.studioRole separates semantics from editable names. Component.studioMotion pins duration/reduced-duration/cleanup; previewContent holds sample text. Six filled/outlined and default/disabled/pressed combinations share one evaluator. Both authoritative transactions and direct projection/export validate global stable IDs and references.

Delivery supports whole conflict-free file plans; partial hunks remain unsupported. generatedRelease is separate from installedRelease, which remains null without independent verification. Expo 57.0.17/RN 0.86.3 uses React 19.2.3 in its own locked consumer. SwiftUI targets iOS17+ with Swift tools6.0/Swift6.3.3 candidate and UIKit announcements. Compose pins AGP9.0.1, Gradle9.1.0, JDK17, Kotlin/compiler2.2.10, BOM2026.08.00 and SDK36. [Dependency decisions](../implementation/studio-dependency-notice.md) record licenses and evidence. esbuild@0.28.2 is the sole permitted workspace dependency build script; verification installs locked dependencies with ignore-scripts.
