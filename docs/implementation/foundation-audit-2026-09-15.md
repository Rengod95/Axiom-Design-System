## Findings that affect the next editor increment

1. **Component creation was coupled to five Axiom token IDs.** `createCatalogSources` in [studio-catalog-sources.ts](../../modules/ads-core/src/studio-catalog-sources.ts) selected `token.content`, `token.surface`, `token.border`, `token.radius` and `token.fontSize` solely by ID presence, then used literals when absent. Compatible imported/authored semantic tokens were ignored; a misleading canonical ID could also make a new component invalid. The change supplement addresses this bounded default-selection defect. It does not impose a universal token name or token-count minimum. [SYN03](../foundation/syntax/foundation-and-token-semantics.md) permits valid literals unless an applicable user policy forbids them.
2. **Part and Slot are different contracts and should not be merged in source.** [CMP05](../foundation/components/parts-slots-and-instances.md) distinguishes logical Part, a Slot owned by a Part, replaceable Part permission, rendered node, and version-pinned Instance. Slots carry content kinds, cardinality, default content and allowed contracts; Instances carry values, slot contents, overrides and provenance. The pre-increment UI exposed Part and Slot jargon in [component-inspector.tsx](../../apps/studio/src/component-inspector.tsx), but slot creation in [studio-component-mutations.ts](../../modules/ads-core/src/studio-component-mutations.ts) used fixed text/component content kinds and empty defaults/allowed contracts. [studio-catalog-validation.ts](../../modules/ads-core/src/studio-catalog-validation.ts) also requires empty replaceable-parts/override permissions and rejects general slot content contracts. Renaming or merging controls cannot implement the missing semantics.
3. **An intuitive Elements tree can preserve those source boundaries.** Present selectable visual elements first, with layout/style/text editing for the selected element. A secondary “accept external content” setting can expose the Slot contract. Stable IDs, technical roles and contract restrictions belong in advanced details. “Insert an instance” and “duplicate a definition” must remain distinct operations. Do not offer an element type that the actual renderer and source validation cannot represent.
4. **Connections is implemented and useful, but starts at the wrong level.** [token-relationships.tsx](../../apps/studio/src/token-relationships.tsx) follows active-theme whole/property/composite references, renders dependency edges, reports theme override provenance, and navigates exact component/Part/design-property usages. Its global tree starts from literal roots and can expand to 512 nodes with a depth bound, overwhelming the common selected-token task. A selected path of “Value source → selected token → Used in” with a secondary all-connections view would expose its existing value. Changing a binding must still use the typed token editor. These token relationships do not implement CMP07 Host/Instance connection authoring.
5. **Domain binding compatibility is not the user policy engine.** `isStudioTokenCompatible` in [studio-style-values.ts](../../modules/ads-core/src/studio-style-values.ts) enforces the exposed token's declared domain purpose and data type. Unknown/unclassified imports retain the documented type-only compatibility fallback. However, [foundation-validation.ts](../../modules/ads-core/src/foundation-validation.ts) explicitly rejects nonempty `policies`. Required-token usage, Canvas violations, recorded exceptions, expiry/approval and release gating from SYN03/UX05 remain open.
6. **The appearance precedence profile differs from the full Foundation contract.** [CMP10](../foundation/components/appearance-conditions-and-precedence.md) gives explicit priority and refinement their normative roles. The bounded `projectStudioDesign` in [studio-presentation.ts](../../modules/ads-core/src/studio-presentation.ts) ranks specificity before explicit priority and [studio-validation.ts](../../modules/ads-core/src/studio-validation.ts) forbids nonempty `refines`, arbitrary conditions and environment selectors. [ADR-0014](../adr/0014-studio-authoring-and-target-delivery.md) documents the bounded variant/state/priority scope. Closing this difference requires compatibility/version planning and regression fixtures, not a silent precedence flip for saved projects.
7. **Visible catalog coverage is not complete upstream behavior.** The catalog retains 239 canonical entries, 330 provider rows and 209 independently creatable components. The current source has 113 bounded semantic contracts and 96 specialized structural adaptations with explicitly unimplemented runtime contracts. [studio-catalog.test.ts](../../modules/ads-core/test/studio-catalog.test.ts), [catalog-capabilities.ts](../../modules/target-packs/src/catalog-capabilities.ts) and the renderer distinguish these. Do not claim that an SVG, source structure or a native HTML adaptation is the original provider's runtime implementation.

## Change supplement — baseline token connection

After recording the findings, the owner-authorized increment changed only default token selection in [studio-catalog-sources.ts](../../modules/ads-core/src/studio-catalog-sources.ts), with focused coverage in [studio-catalog-foundation.test.ts](../../modules/ads-core/test/studio-catalog-foundation.test.ts).

- A canonical baseline ID remains preferred when it is not deprecated, has the correct type/domain purpose and renders in the default context and every named ThemeSet.
- Without that canonical default, exact optional intent names may match. The bounded list covers content/foreground, surface/background, border color, radius and font-size roles. `semantic`, `color` and `colors` path namespaces and recorded DTCG import prefixes are supported. Arbitrary suffixes such as `danger.text.primary` are not stripped into a generic text role.
- Explicit Semantic-tier or alias/expression candidates rank before unclassified literal candidates; ordered intent preferences are deterministic. A tie between equally suitable candidates keeps the existing literal fallback instead of guessing by token order or ID.
- `isStudioTokenCompatible` remains the shared authority for type and exposed-domain purpose. An alias is classified by its own declared domain, not the primitive target. Unclassified DTCG imports retain type compatibility; this does not infer or write domain metadata.
- New defaults only select supported numeric in-gamut sRGB and bounded px dimensions. A token that becomes an unsupported value in a named theme does not get silently attached. General source interpretation and all candidate graph validation remain unchanged.
- The operation writes references into new proposed designs only. Foundation IDs, values, aliases, theme overrides, original source bytes and existing component designs are untouched. Opening a creator or constructing a plan does not commit data. An empty Foundation can still produce a valid component using literals.

The eight focused tests passed on 2026-09-15. They cover renamed canonical IDs, authored semantic aliases with opaque IDs and live theme changes, prefixed DTCG import, incorrect canonical type/domain, exposed-alias domain semantics, ambiguous candidates/order independence, deprecated and unsupported values, named-theme renderability, empty Foundations and source preservation. The existing catalog suite also passed all 12 tests (including all 209 independently creatable components, source preservation, reviewed transactions, replay and undo/redo). This run took approximately 51 seconds and was not a product-wide gate.

This addresses the baseline-ID coupling finding for newly created catalog/custom-layout components. It does not implement general user policies, a semantic intent registry, arbitrary typography-composite projection into font-size references, automatic migration of saved components, or the remaining Foundation matrix. New template/creator/Elements/Connections UI work has separate ownership and must not be counted complete merely because this core supplement exists.
